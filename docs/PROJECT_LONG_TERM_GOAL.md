# 《深渊苏醒》统一灰盒目标

## 当前唯一目标

先把《深渊苏醒》收敛成**一个能连续玩的 3/4 斜俯视灰盒 RPG**。当前优先级是可操作、可碰撞、状态有变化、反馈清楚、可成长；画面只用统一的简单像素占位，不接入概念图、城市贴图包或互相割裂的实验画风。

玩家体验要集中在一条循环：

**在家准备 → 出门探索 → 采集/挖掘 → 制作与装备 → 战斗/拾荒 → 扛过黑夜 → 击败区域 Boss → 带奖励回家 → 解锁下一块区域。**

每个动作至少要有输入、碰撞或目标判定、状态变化、即时可见反馈、奖励去向和可重复游玩的理由。只有静态画面、代码文件、菜单按钮或自动化断言，不算玩法完成。

## 五款参考游戏都要进入同一个游戏

只学习体验结构，不复制作品的角色、地图、美术、文本或原样内容。

| 参考 | 《深渊苏醒》的最小可玩闭环 |
|---|---|
| Minecraft | 网格采集/挖掘、资源掉落进背包、放置防御、工作台制作；世界操作必须和碰撞网格一致。 |
| Terraria | 武器/防具成长、装备门槛、可读的 Boss 阶段与区域事件；Boss 奖励开启下一段探索。 |
| Stardew Valley | 一种作物从种下到收获、一种鱼的咬钩操作、一份烹饪食物与 buff、一次居民送礼反馈。 |
| Don't Starve | HP、饥饿、Sanity、日夜与光照压力；黑暗/夜晚改变风险，不能只做装饰条。 |
| Crashlands | 图纸解锁、任务推进、怪物掉蛋、孵化、宠物跟随并协同战斗/采集，至少一条成长或进化分支。 |

它们共享同一角色、背包、物品 ID、世界、任务进度和存档；不做五个互不相干的小玩法。

## 一个版本与清理规则

- 玩家只接触一个正式入口和一个当前灰盒场景；不再增加 V22/V23、pass 编号或新的平行测试游戏。
- 玩家只需要打开根目录 `index.html`；它是唯一游戏入口，进入 `prototypes/successor-3-4/live-candidate.html`。开发检查页和美术实验不是额外版本。
- 候选借用 V21 的模拟、存档和现有 Relay。公网构建与上线状态仍需独立检查；没有部署证据时不称为已发布。
- V21 的 UI 模板已经改名为 `ui-shell.html`，独立旧游戏入口已从活动工作树移除。V21 和 UI 壳仍被当前游戏实际加载，保留到替代实现经过完整验证。
- 当前玩家入口不加载概念图、城市美术包或其他候选场景。以后若更换素材，必须一次性按统一像素规格、锚点和碰撞关系接入。

## 模块必须有唯一状态主人

以 [`SUCCESSOR_MODULE_MAP.md`](SUCCESSOR_MODULE_MAP.md) 的 canonical owner 表为唯一模块清单。禁止为“看起来模块化”而复制一套状态或将一个系统拆成许多空文件。

| 主人模块 | 唯一负责的状态 | 允许的跨模块交接 |
|---|---|---|
| Core State & Save | 版本化角色/世界存档与迁移 | 只保存领域模块提交后的状态。 |
| World & Terrain | 网格、地形、阻挡、合法位置 | 提供碰撞/坐标查询；不发物品奖励。 |
| Interaction & Gathering | 交互目标、距离、采集阶段请求 | 向世界查合法目标，向奖励/背包请求结算。 |
| Items & Inventory | 物品定义、堆叠、装备、库存变更 | 对制作、采集、钓鱼、农作统一原子结算。 |
| Crafting & Processing | 配方、图纸、工作台条件、材料消耗 | 通过背包接口提交材料与产物。 |
| Combat & Weapons | 攻击窗口、命中规则、伤害结果 | 确认事件交给 Creatures & AI；表现层只订阅事件。 |
| Creatures & AI | 怪物生命、行为阶段、Boss 阶段与死亡 | 通过 Loot & Rewards 发起一次性掉落。 |
| Loot & Rewards | 掉落规则、唯一奖励与蓝图/蛋 | 交给背包结算，自己不直接改库存。 |
| Survival & Needs | HP、饥饿、Sanity、食物效果 | 接收已确认的伤害/食用事件。 |
| Farming & Food | 作物阶段、收获请求、烹饪输入 | 物品增减由背包处理，饱腹/效果由生存模块处理。 |
| Pets & Companions | 孵化、宠物状态、跟随与协同请求 | 战斗走 Combat，采集走 Interaction，奖励走 Loot。 |
| Quest & Narrative | 目标状态、线索、区域解锁条件 | 使用领域事件，不直接改战斗、库存或地图坐标。 |
| Network & Co-op | 既有 Relay 消息与房间传输 | 不成为游戏规则、存档或物品所有者；协议先保持兼容。 |
| Rendering & Camera / Animation & Presentation / UI & Map / Audio & Feel | 只显示已确认状态和事件 | 不反向决定奖励、命中或任务完成。 |
| Integration & QA | 跨模块验收证据 | 一个入口、一个检查清单；不拥有领域状态。 |

每个实现任务只指定一个主责 owner，并写清事件/请求契约、配合方、文件范围、失败处理和验证项。先闭环一个小区域，再按这张表接系统；不做“一次拆完一百个文件”的空架构。

## 分段计划与粗略工时

以下是**集中开发工时估算**，不是倒计时承诺；已有 V21 能复用的逻辑会缩短工时，联机/存档跨模块问题会延长工时。先交付阶段 1 的小循环，再逐段扩大。

| 阶段 | 估算 | 可验收结果 |
|---|---:|---|
| 0. 版本归一与模块盘点 | 2–4 小时 | 一个灰盒入口；旧入口依赖表；UI 壳和运行时依赖有清楚职责；候选贴图不再混进当前画面。 |
| 1. 采集到制作 | 4–6 小时 | 3/4 格子移动/碰撞；木材 3 次、石头 4 次采集；每次有数字/震动式视觉反馈；最后一次才结算背包；宝箱、工作台和一件工具组成闭环。 |
| 2. 出门、战斗、过夜、Boss | 6–10 小时 | 一个可探索区、一种普通怪、一场有阶段提示的 Boss 战、一种防御建造；HP/饥饿/Sanity/灯光和昼夜会影响决策；Boss 奖励开新路线。 |
| 3. 星露谷式生活支柱 | 6–10 小时 | 一种作物可种/成长/收获；一条钓鱼咬钩小玩法；一份可烹饪食物有明确 buff；一个 NPC 礼物/交易反馈；技能有实际效果。 |
| 4. 崩溃大陆式伙伴成长 | 6–10 小时 | 一条任务/图纸链；怪物掉蛋、孵化、命名、跟随；宠物协同采集或战斗；至少一个成长/进化节点。 |
| 5. 集成与联机验收 | 8–12 小时 | 保存/重载；房间中两名玩家完成同一采集、战斗、奖励与区域解锁；断线恢复检查；修复跨模块重复奖励与不同步。 |

**约 32–52 小时**可以争取形成五类参考体验各有一个最小闭环的单区切片；这不等于完整商业游戏。若只能投入 2–4 小时，优先交付可操作的一次“采集 → 制作工具 → 打败一只怪 → 回家”的灰盒体验，鱼、农场、宠物和完整联机验收不冒充完成。

## 画面边界

- 本阶段只用一套统一灰盒色板、同一 3/4 投影、地面/阻挡/物件/角色层级；不追求高精美场景，不接生成的整张背景图。
- 画面只需清楚区分可走、可挡、可交互、危险和奖励；资源受击、角色受击、Boss 阶段必须有明显但轻量的反馈。
- 当前用户报告的蓝墙、城市贴图串场、黑色地图外区、画面抖动和空场景仍是待运行时复核的问题；源码/离线绘图不能代替真实页面和普通操作验收。

## 证据与交接要求

所有进展用 `VERIFIED / REPORTED / PLANNED / UNKNOWN` 区分。明确写出实际入口、真实输入完成了什么、数据是否落到背包/存档、第二客户端是否观察到变化。HTTP 200、生成图片、模块文件、VM 测试或单机 presence 都不能单独证明玩法/联机完成。

旧工作区在每次清理前先有可回退快照；不删仍被正式入口、V21 loader、发布脚本或测试使用的文件。当前目标是少入口、少运行时分支、模块 owner 唯一、一个真实可玩闭环。
