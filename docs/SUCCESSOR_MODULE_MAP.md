## How to read this map

- [`MODULE_MAP.md`](../MODULE_MAP.md) maps the ordered **V21** runtime. Treat it as the legacy behavior, compatibility and test baseline, not the target renderer.
- The player route is root [`index.html`](../index.html) → [`live-candidate.html`](../prototypes/successor-3-4/live-candidate.html). It loads the V21 simulation inside an iframe and installs the camera adapter, graybox scene painter, interaction work module and 3/4 renderer. It is one presentation over the shared runtime, not a second version. The former `prototypes/successor-3-4/index.html?view=...` variant chooser now redirects to the root entry.
- `prototypes/successor-3-4/preview.js` remains an isolated developer diagnostic with Relay/storage guards. It is not the player route and should not be used as the game link.
- `successor-renderer.js` still combines projection, terrain, props, actors, mobs, resources, HUD-related preview changes and device input. Stage 1 moved development QA controls/input sequencing/diagnostics to `qa-harness.js`; the renderer exposes only a guarded local-preview bridge. It remains proof code, not a modular final architecture. Do not expand it into the whole game as one file.
- `V21 baseline` below tells the next owner where to inspect existing behavior. `Successor proof` tells what the guarded preview currently demonstrates. `Successor target` is a proposed future module boundary, not an implemented API.
- Paths, tests, and ownership must be rechecked against the live worktree before each implementation. Dirty or untracked files with unknown provenance are protected.

### Cross-module transactions

- **Enemy reward:** Combat confirms an accepted hit/damage event → Creatures applies it to mob HP and emits defeat once → Loot & Rewards selects a unique award → Items & Inventory applies it → Animation/Audio/UI observe the confirmed result.
- **Quest reward:** Quest confirms objective completion and its fixed reward ID → Loot & Rewards validates the grant request → Inventory applies it. No NPC dialogue or UI button grants items directly.
- **Gathering:** Input sends one intent → Interaction & Gathering checks target/range and node availability → World & Terrain validates legal space and POI & Exploration supplies place/discovery context → Loot & Rewards decides any explicitly authored award eligibility → Items & Inventory applies the item change. Ownership and persistence for depleted shared resource nodes remain undefined and require a separate contract before implementation; do not invent another canonical owner.
- **Food:** Farming/Fishing creates ingredients → Inventory stores them → Crafting & Processing validates a recipe and requests one atomic exchange → Survival & Needs applies cooked-meal effects and persists only its timed buffs; item counts remain Inventory-owned.
- **Player survival:** Combat confirms player damage → Network delivers the existing approved event → Survival applies HP/sanity and any zero-HP state transition → Items applies any explicitly owned inventory penalty → HOME/World provides a valid recovery location → Core State & Save persists the result. Network transport is not health authority, and Survival never mutates inventory counts or world coordinates.
- **Station crafting:** HOME owns station placement/identity → Crafting checks recipe and station → Inventory commits item changes atomically.
- **Visuals:** Domain owners emit confirmed state/events → Animation/Audio consume them → Rendering & Camera draws snapshots. Art pixels never own collision, interaction, AI or reward rules.

Every player-visible feature task must also include an **art/readability deliverable**: asset/content IDs, source dimensions and anchors where applicable, intended native pixel density, target display size and a runtime review plan for 1280×720 and 390×844. Keep high-detail pixels crisp; mark any untested or visibly blurry/coarse-mosaic result REVISE/UNKNOWN. A user-designated art contributor supplies candidate source art (a creative role, not an owner); Asset Pipeline checks source/metadata, Rendering & Camera checks display/projection, and the user resolves product-direction choices. None of these roles may decide gameplay/domain state.

Existing module cards remain DRAFT and are subordinate to these owner boundaries. Before implementing a card whose wording conflicts with this section, update the card and define the interface; do not infer an alternate owner from a stale card.

## Current preview boundary verified from source

The isolated `preview.js` diagnostic contains a save adapter backed by its own `abyssal_wake_successor_preview_v1:` browser-storage namespace and a fail-closed WebSocket guard. Refreshes in the same browser profile preserve this preview's save without touching the live V21 save keys; disabling browser storage falls back to memory and is reported. Its old variant-selector page redirects to the root game, so it is not an alternate player route. The live candidate instead uses the real V21 runtime and Relay/save setup, then injects the 3/4 camera, shared scene painter, interaction-work module and renderer.

Therefore:

- **VERIFIED source:** the preview reuses real V21 gameplay state and selected world/collision behavior behind a local guard.
- **VERIFIED source:** the camera adapter maps display projection and input while V21 world coordinates remain the underlying state.
- **VERIFIED source:** successor runtime rendering/input still sits mainly in `camera-adapter.js` and one large `successor-renderer.js`; guarded QA controls and diagnostics are isolated in `qa-harness.js`.
- **NOT PROVEN:** production entry, real multiplayer, persistent saves, broad module separation, complete game-loop ownership, acceptable final visual quality, or V21 retirement.

## Art contributor role (not a canonical module owner)

The user may designate a separate AI or artist to create original visual source art. This **art contributor** is a production role, not an extra code/module owner. It works only in the explicitly assigned candidate-art paths from an approved visual brief. **Asset Pipeline** owns source intake, metadata, validation and manifests; **Rendering & Camera** owns projection, sampling and in-game visual acceptance; the user owns product direction and candidate selection. The contributor must not edit runtime code, collision, manifests, save data or Relay contracts. If a source/display contract is not agreed, return a visual study for review instead of guessing production dimensions.
