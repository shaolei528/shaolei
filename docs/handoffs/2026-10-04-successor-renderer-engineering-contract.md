## Proposed high-detail pixel-art baseline

- Keep the selected broad 3/4 oblique view. A 64×64 logical world cell projects to a 64×32 screen diamond. The projection is presentation-only; simulation distances and map/collision units do not change.
- Preserve source pixels and use nearest-neighbor sampling. Prefer native 1× or integer enlargement; when the viewport cannot fit an integer scale, keep a crisp internal pixel viewport with letterbox/safe margins instead of stretching pixels unevenly. Exact zoom tiers require art-lead review against desktop and phone captures.
- Propose 32×48 as the minimum character-frame study size and 64×64 or 96×128 as higher-detail alternatives. These are source-frame proposals, not a frozen production atlas. Review character silhouette, face/clothing clusters, animation readability, prop scale and ground detail together at actual display size.
- Use bottom-center foot anchors for actors and ground-contact anchors for props. Stable world-space foot depth (`worldX + worldY`, then stable object ID/order) is the initial sorting key. Large buildings register a ground footprint and explicit front/behind occlusion bands; visual alpha never defines collision.
- Keep HUD outside viewport safe insets and touch-control zones. Produce distinct 1280×720 and 390×844 compositions; do not shrink desktop HUD uniformly onto phone.
- Every animation sheet declares frame dimensions, direction/action rows, frame count, frame duration and anchor. Missing/failed sheets report status and use a valid static frame-0 or explicit placeholder fallback. Fallback status must be visible in developer preview.

## V21-normalized camera input correction - 2026-10-04

- **Correction to prior test claim:** the earlier projected-speed test exercised `worldDeltaForScreenIntent()` in isolation. The live renderer instead fed `screenIntentToWorld()` to V21, whose `simulation-update.js` normalizes world joystick magnitudes above one. The old test therefore did not prove equal speed on the integrated route.
- **CONFIRMED source cause:** the inverse 2:1 transform yields world-input lengths sqrt(2) for horizontal screen cardinal intent and sqrt(8) for vertical screen cardinal intent. V21 clamps both to unit world speed before multiplying by its existing 154/146 speed. Projection therefore made horizontal cardinal movement twice as fast as vertical cardinal movement, absent collision.
- **Successor-only correction:** `worldIntentForScreenInput()` scales the inverse vector by `1/sqrt(8)`. Its output magnitude never exceeds V21's normalization threshold, so the canonical V21 movement and collision chain applies it unchanged. All eight screen directions now have equal projected speed at V21 speed divided by sqrt(8); faster directions are reduced to the previous slow-direction rate. Dash uses the same camera compensation. No gameplay owner, world position, collision, save or network contract changed.
- **CONFIRMED regression:** the successor camera test reads and asserts V21's actual `if(l>1)` movement normalization, passes all eight compensated inputs through that rule, checks equal projected speed and checks the runtime bridge uses the compensated vector. This is mathematical/source integration evidence; sustained browser/phone movement remains **UNKNOWN** because current automation only sends brief key presses and short drags.
- Prior heading `Projected movement-speed regression` records the initial incomplete unit test; this section records the subsequent integrated source finding and corrected regression.
