## 1. 长期项目目标

制作一款有生活感、清楚好读、操作顺手的现代沿海城市合作生存沙盒 RPG：玩家在温暖安全的 HOME 生活、整理物资、结识居民并准备出发；到 OUTSIDE 探索城市 POI、应对生存压力、战斗或避开危险、带回物资和线索；回家后修复营地、制作装备、帮助居民，并开启新的地点和故事。

五款参考游戏只提供设计经验，不复制其专有角色、世界、画面、关卡、配方、UI 或完整系统。作品自己的特色是：

> **现代城市生活逐渐被深渊侵蚀；玩家一边过日子，一边为下一次冒险做准备。**

目标视觉为 **Modern High-Detail Pixel Art**，目标镜头为用户选定的 3/4 斜俯视。实际游戏画面须保持锐利、细节可读，不能因素材缩放、压缩或渲染而糊成粗马赛克。恐怖逐步升级：熟悉的现代城市 → 小异常 → 设施故障 → 怪物 → 深渊觉醒 → 文明崩坏。

## 2. 五款参考游戏如何转化为本作经验

| 参考 | 学习的体验 | 转化为本作 | 不照搬 |
|---|---|---|---|
| Crashlands | 战斗反馈迅速，敌人有个性，掉落能推动制作与故事 | 让敌人动作容易读；每种战利品能解释用途；先做少量有特色的生物 | 搞笑基调、角色/怪物设计、原作剧情和配方 |
| Terraria | 探索会发现东西，工具和成长会打开新区域，挑战层层推进 | 做紧凑城市 POI；用工具、线索和营地升级打开新路线；逐步铺向首个大型威胁 | 巨型地图、装备数量膨胀和未验证的 Boss 长阶梯 |
| Minecraft | 玩家能表达自己；家园改变后续准备和玩法 | 先做少量可见营地升级：照明、储物、制作、防护；让每项升级服务下一趟出发 | 无边界方块目录、尚无共享权限规则的多人自由建造 |
| Don't Starve Together | 准备和环境压力让出行有取舍；合作能分工 | 昼夜、食物、理智和区域危险提供明确警告；合作玩家能侦察、战斗、搬运和互助 | 不透明惩罚、新手看不懂的衰减和挫败式永久损失 |
| Stardew Valley | 日常、居民、关系和社区成长让玩家想回家 | 先做有实际作用的居民，再增加日程、请求、种植、动物和社区修复 | 在生存主循环尚未稳定前就做大型恋爱/日历模拟 |

组合顺序不是“五款游戏各复制一套”：**Crashlands 的清楚战斗 + Terraria 的发现成长 + Minecraft 的有用家园 + Don't Starve 的可读准备 + Stardew 的居民日常**，共同支撑 HOME → OUTSIDE → HOME。

## 3. 模块共同规则

每个系统模块都必须有一个明确的状态负责人。其他模块只能通过它公开的函数、命令或事件读写，不得偷偷复制一份相互竞争的权威状态。

1. **一个模块一个主责。**任务可以跨模块，但必须指定一个主责模块及配合模块。
2. **接口先讲清。**写明谁发起、谁验证、谁改状态、谁保存、谁显示结果，以及失败时如何反馈。
3. **不做循环依赖。**例如 UI 可以请求攻击，但 UI 不决定伤害；动画可以监听命中事件，但不能制造命中。
4. **机制与表现分开。**碰撞、伤害、掉落、任务完成、存档和联机权威必须来自玩法模块；画面和音频读取已发生的结果。
5. **内容与规则分开。**物品、配方、NPC 台词、怪物数值等逐步数据化；规则代码解释数据，不把整本内容表塞进一个巨大函数。
6. **本地、共享和持久化分层。**玩家本地状态、多人实时消息和未来持久世界不是同一种数据；不能把 Relay 在线就说成共享世界存档。
7. **兼容优先。**动现存 V21 模块之前检查启动顺序、现有合同和测试。存档字段、Relay 事件名/载荷、输入行为等不得顺手改掉。
8. **一次一个可验收切片。**先打通小流程，再扩展数量；不能同时要求一个 AI 改战斗、NPC、背包、存档和联网。
9. **新功能不等于已上线。**草案标记 DRAFT；代码存在但没从 V21 入口运行标记为未接入；测试通过也不等于手机/多人体验验收通过。
10. **美术按真实游戏尺寸验收。**原图分辨率不代表游戏内清晰。检查素材合同、nearest-neighbor 渲染、角色/地面比例，并与游戏运行画面对照。

**推荐交接规则：**AI 领取任务时，把表里的模块状态当作开工线索，再以当前 `survival-v21.html`、模块源码、合同和测试重新确认；若实现中发现状态不同，先报告证据并更新状态，不要为了匹配这张表擅自重构。

## 5. 建议的依赖关系

以下是**逻辑依赖**，不是要求马上创建目录或重写 V21。方向箭头表示“调用/订阅”，不是让下游模块反过来拥有上游数据。

```text
核心状态 / 角色
  ├──背包与装备──制作与加工──HOME升级
  ├──战斗意图──战斗结算──怪物与掉落
  └──存档适配器（只保存各模块公开的数据片段）

世界 / 地形 / 碰撞──POI与探索──任务与叙事
          ├──采集与搜刮──物品
          ├──怪物AI──战斗结算
          └──渲染适配（画面不能反向决定规则）

NPC──对白 / 交易 / 请求──任务
宠物与动物──同行能力 / 照料产出──战斗或物品接口（分开权威）
生存──时间天气 / 食物 / HOME恢复

UI与设备输入 → 游戏意图 → 领域模块 → 已确认事件 → UI / 动画 / 音频
                       └── 联机适配器 → 其他客户端
存档主控 ↔ 各领域模块的版本化数据片段
集成与QA → 检查上述接口与整条可玩流程
```

最重要的共用接口约定：

- **命令/请求**表达玩家想做什么，例如 `requestAttack(targetId)`、`requestCraft(recipeId)`、`requestInteract(targetId)`。
- **已确认事件**表达系统确实做了什么，例如 `hitConfirmed`、`itemAdded`、`poiDiscovered`、`homeUpgradeCompleted`。
- **查询**只读状态，例如 `getInventorySnapshot()`、`getNearbyTargets()`、`getPoiStatus(id)`。
- **序列化片段**由状态拥有模块定义版本；全局存档协调写入和迁移。
- **渲染/声音只订阅事件与只读快照**，不把表现结果回写为机制结果。

V21 浏览器全局模块是现存兼容基线，不是 successor 的永久架构。Successor 可以复用经过验证的玩法 owner，但 projection/render/input/presentation 与 QA 边界须能单独检查和回退。是否独立文件、是否 ES module、如何加载，都须依 successor 实际 loader 验证；不要整体搬动仍有用的 V21 文件。

## 6. 分阶段目标：从一条可玩的路线逐渐扩充

### 阶段 0：建图，不改代码

- 以 `MODULE_MAP.md` 核对 V21 基线，以 `SUCCESSOR_MODULE_MAP.md` 核对 successor preview 的真实接线；逐模块标出已接入、继承、缺口或 PLANNED。
- 每项记录 V21 基线文件、successor 文件或 GAP、唯一状态 owner、已存在/待冻结接口、相关回归测试和美术/工程文件边界。
- 清点存档、Relay、移动输入、碰撞坐标、素材规格和预览/正式 gate；五款参考只作为体验来源。
- 验收：新 AI 能看懂“模块当前在哪、接手哪个 successor 文件、不能越过哪个 owner、如何验证”，不会把 guarded preview 或计划功能误称为正式系统。

### 阶段 1：模块化 successor，再完成 HOME → POI → HOME 垂直切片

- 先将 successor proof 中的投影/输入、场景绘制、HUD 与本地 QA 控制分出清楚边界；不能把整款 successor 继续塞在 `successor-renderer.js`。
- HOME 准备物资与装备；沿一条清楚路线抵达现代城市 POI；战斗或绕行、搜刮有用资源/线索；回 HOME 获得真实且可见的成长。
- 美术负责人并行准备符合冻结合同的候选；工程负责人接入真实游戏数据与输入/碰撞，两边不编辑同一文件。
- 验收：玩家能理解为何出发、途中发生什么、带回什么、家里如何变好；目标尺寸下画面清楚；重进/失败行为符合兼容合同。单测不代替目标尺寸画面验收。

### 阶段 2：战斗、怪物、动画和音频形成一套完整反馈

- 明确攻击输入、命中权威、怪物意图、受击/死亡结果的事件边界。
- 命中、挥空、受伤、击杀的音画反馈区分清楚；动画与特效无游戏权威。
- 同时验证键鼠/触控、单人模拟和已有多人协议。
- 验收：挥空不假报命中；一次真实命中只结算一次；声音不削波/重复；手机操作不误触。

### 阶段 3：一位 NPC 带出 HOME 社区

- 先有一个有用岗位、一段短日程、一项自愿请求、一种明确的帮助结果。
- 对白只显示领域状态；接受/拒绝/交付请求走任务和物品接口。
- 验收：玩家能说出这个居民为何重要；重进后已承诺的数据按当前存档范围恢复。

### 阶段 4：工具门槛、发现与地区成长

- 增加少量工具、可辨认采集点、POI 线索及一个能被现有装备打开的新选择。
- 任务读取发现/采集结果，不复制它们的状态。
- 验收：新区域解锁由明确条件触发；地图、关卡提示和实际碰撞区域一致。

### 阶段 5：宠物伙伴与专门的动物/种植循环

- 先做一种探索或战斗伙伴，能力范围明确、可召回、多人表现一致。
- 再做一项能补充远征的食物来源；验证它解决的玩家问题。
- 验收：同行伙伴不代替权威命中；农场产物有消耗/准备去处；不为“像参考游戏”而空加系统。

### 阶段 6：更深区域、世界阶段和 Boss

- 只有前面的玩家循环稳定后，再扩地区、世界事件、Boss 和长期成长。
- 每个阶段改变世界的方式必须可读、可回归、可回退；共享世界权威与持久化先有独立设计合同。
- 验收：内容扩张仍强化 HOME/OUTSIDE 循环，不让新手被突然的全屏深渊或不明规则淹没。

## 8. 每个模块交付卡必须回答

1. **玩家价值：**玩家会做什么？它让 HOME、探索、生存、战斗、成长或合作的哪一处变好？
2. **状态 owner：**谁拥有唯一真相？哪些状态由其他模块只读？
3. **接口：**输入请求、输出事件、查询、失败状态和数据版本是什么？
4. **范围：**本模块本轮负责哪些文件/内容？明确不包含什么。
5. **依赖：**其它模块要提供什么服务？是否会造成循环调用或双重结算？
6. **保存/联网：**是本地临时、玩家持久、世界持久还是多人实时？谁裁决冲突？
7. **体验与视觉：**实际游戏尺寸下能否读懂？触控能否操作？恐怖阶段与 HOME/OUTSIDE 色彩是否正确？
8. **验证：**一个成功例子、一个失败边界、一个相邻模块回归和真实运行证据。
9. **交接：**VERIFIED / REPORTED / PLANNED / UNKNOWN 分开写；下一 AI 从哪份文档和哪个 commit 接手。

缺少状态 owner、边界或验证方式时，模块先保持设计草案，不要让 AI 靠猜实现。
