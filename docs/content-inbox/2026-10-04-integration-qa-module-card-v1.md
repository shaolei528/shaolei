# Integration & QA 模块卡 V1

**状态：DRAFT / NOT IMPLEMENTED（流程和模块边界草案）**  
**主责模块：**Integration & QA  
**协作边界：**按当前 gate 只列被测的 canonical domain owners；不得在某个具体任务里默认拉入全部模块。Rendering & Camera、Asset Pipeline、Network & Co-op 只在相关范围内配合。  
**目标：**让 AI 自己负责找证据、确认问题、做安全修复并验证相邻系统；用户只需决定产品方向，不需要读代码或整理日志。

## 玩家价值

玩家看到的不是“测试数量”，而是能稳定进入游戏、操作可信、素材接入后仍清晰、修复不会悄悄破坏其它玩法。QA 的最终问题是：目标玩家路径是否按预期工作，失败时游戏是否安全地提示和恢复。

## 当前测试方式可确认的范围

以本次检查的本地工作区为准，必须在以后每次开工重查：

- package.json 定义了资产验证、Worker dry-run 和 live Relay 脚本，但没有统一的 npm test 命令。
- GitHub workflow 按相关文件路径启动，包含一组 Node 回归、模块语法检查、loader 检查和资产 gate。Workflow 覆盖是所选脚本的集合，不等于运行仓库中每个测试，也不等于浏览器/手机/双客户端验收。
- tests 下存在多类 Node fixture，部分用 VM、fake WebSocket 或数据夹具。它们适合验证确定逻辑和回归，不会自然证明真实浏览器事件、音效听感、像素清晰度或线上网络。
- 本卡不把当前 dirty worktree 视为稳定基线。分支、HEAD、未提交改动和文件来源每次必须现场核对；测试结果要记录所用工作副本与命令。

## QA 状态标签

每条发现选一种主要标签，并写明证据范围：

- **CONFIRMED BUG：**可稳定复现，或源码与有效回归测试共同证明错误行为。写复现条件、预期/实际、影响和修复验证。
- **SUSPECTED：**源码/报告提示风险，但当前无法复现或证据未闭合。写下一步验证方式，不能作为已修复的 Bug。
- **UNKNOWN：**目前无法判断，例如没打开真实浏览器或没有双客户端条件。
- **DESIGN TRADEOFF：**行为可能符合现有合同，但玩家体验需要产品取舍；不要冒充程序缺陷。
- **REGRESSION：**修复或相邻代码出现了先前没有的错误；立即停下扩展，确认根因和受影响范围。
- **PASS WITH SCOPE：**只写实际通过的测试/设备/入口范围。不要用笼统的“QA 通过”掩盖未测部分。

红色字、浏览器 console warning、CI 失败、文件命名异常或静态分析提示都只是线索。先判断错误来源、发生条件、是否影响玩家；不要把所有红字都算游戏 Bug，也不要因为游戏能启动就忽略稳定的错误。

## 模块职责与边界

| QA 责任 | Integration & QA owns | 领域模块仍 owns |
|---|---|---|
| 复现、严重度和影响记录 | 统一证据格式、风险排序、交接 | 自己的规则正确性和模块接口 |
| 回归验证 | 选择必要且有意义的测试矩阵，检查相邻模块和玩家路径 | 领域单测、规则合同、实现 |
| 跨模块流程验收 | 核对模块组合、V21/successor 入口、浏览器/设备边界 | 玩法状态所有权，不能交给 QA 造假 |
| 发行准备 | 汇总通过项、已知问题、未验证项与 blocker | 版本/资产的实际签收和发布决策 |
| 日志与自动化 | 提供可复现步骤和机器可读结果 | 不隐藏错误、不为了绿色关闭真实检查 |

QA 不修改玩法来让测试变绿，不删除失败测试，不放宽资产/安全 gate 来绕过 blocker，也不以自己的报告取代用户对游戏风格和玩法方向的取舍。

## 每个 Bug 的执行闭环

1. **保护现场。**检查分支、HEAD、git status、diff、相关用户/并行改动；不要 reset、stash、clean、删除或覆盖未归属文件。记录复现版本。
2. **定义预期。**读合同和相邻调用点，明确玩家做了什么、应该发生什么、实际发生什么、是否违反已确定规则。
3. **确认根因。**先运行最小可复现用例；失败须证明是目标行为而非测试 fixture 错误或并行修改造成。不能复现就标 SUSPECTED/UNKNOWN。
4. **限定修复。**指定一个主责模块、一个根因和最小必要文件范围。不要顺手重构、改 unrelated UI、存档或协议。
5. **先保留回退。**在安全的分支/补丁上工作；若目标文件正被并行修改且来源不明，不在同一共享差异上叠写，先找不冲突的验证工作或交接清晰的补丁。
6. **验证原错误消失。**复现用例应从失败转为通过；不允许只增加一个不会失败的测试就声称修复。
7. **检查回归面。**运行同模块测试、调用它的相邻模块测试、语法/启动检查；按影响增加完整用户流程验证。高风险接口检查存档、网络、键鼠/触控、渲染或资产合同。
8. **审 diff。**检查变更范围、意外文件、调试代码、错误吞掉、测试被跳过、重复触发、竞态/清理和返回行为。
9. **准确交付。**报告修复了什么、玩家影响、运行过的命令与结果、哪些设备/流程未测、风险和可回滚点。没有实际验证就写 UNKNOWN。

安全且局部的确认 Bug 可以由 AI 自主推进，不要让新手决定技术细节。遇到存档格式迁移、Relay 协议改变、权威边界改变、不可逆文件/数据删除、正式资产替换、合并或部署时，先保存现状并说明具体风险及恢复方案；不要把“我不知道技术”转化成让用户替 AI 排错。

## 分层验收矩阵

| 层级 | 能回答的问题 | 证据样例 | 不能单独证明 |
|---|---|---|---|
| 静态/语法 | 文件能解析，导入/全局名基本存在吗？ | node --check、模块映射检查 | 运行逻辑正确、玩家体验良好 |
| 单元/合同 | 规则和边界例子对吗？ | meaningful Node tests、合同校验 | 真实载入器、浏览器渲染 |
| 集成/启动 | V21 当前入口加载顺序和模块连接吗？ | loader 测试、实际启动记录 | 手机、线上 Relay、整条玩法 |
| 浏览器桌面 | 指定分辨率下 UI、交互、渲染和 Console 怎样？ | 真实浏览器截图/操作与复现步骤 | 物理手机、两客户端网络 |
| 移动设备 | 触屏、安全区、缩放、文字和性能如何？ | 真实或明确标注的设备/模拟器数据 | 未测试设备/系统版本 |
| 联机双客户端 | presence、广播、断线恢复、战斗/状态一致性如何？ | 两个独立客户端的可复现步骤 | 服务端权威或长期共享存档 |
| 内容与视觉 | 素材进入 active renderer 后是否清晰统一？ | 原图、合同、运行画面对照及真实尺寸检查 | 只看源 PNG 或 preview manifest |

需要检查玩家闭环时，覆盖 HOME 准备 → POI → 探索/战斗/搜刮 → 返回成长，并至少检查成功路线、一个失败/退出路线、重进或恢复路线。只与目标相关且能说明结论的检查才加入本轮；不为凑测试数量而重复跑无关检查。

## 优先级与处理顺序

- **P0：**数据破坏、启动/进入游戏被阻断、影响所有玩家的严重安全/存档错误。立即保护数据、确认影响并阻止扩大。
- **P1：**主要循环、网络恢复、战斗结算或关键交互可靠性问题。优先做可复现、局部修复和关联回归。
- **P2：**明显但有替代办法的玩法/画面/输入缺陷。进入近期模块任务。
- **P3：**细微瑕疵、主观 polish 或低概率边缘问题。记录后按体验收益排期。
- 视觉模糊、粗马赛克、素材载入失败或样式混乱若破坏当前高画质目标，可提高优先级；不能靠“测试是绿的”忽略。

严重度写玩家影响，不靠 warning 数量或文件行数排序。

## 串行与并行工作规则

- 不同模块可并行，但先将文件范围切开。对同一文件、相同存档 schema、Relay protocol、manifest 或 active renderer 的变更必须协调，不能因两个 AI 都有好意就叠加提交。
- 每次测试要在本次可见的工作副本执行；新出现的文件或代码标 UNKNOWN provenance，先检查 diff。不要以旧聊天报告认领当前修改。
- 如果另一 AI 正做美术，QA 可检查视觉合同和证据，不覆盖或重新制作其候选。图像原稿与游戏内呈现分别验收。
- 未核实外部 CI 状态就写 UNKNOWN。没有自动化触发记录时，不称其“每天已检查”。
