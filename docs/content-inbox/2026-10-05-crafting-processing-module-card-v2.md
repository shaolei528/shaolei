# Crafting & Processing — 独立模块卡 V2

**状态：DRAFT / PLANNED / NOT IMPLEMENTED as a separated successor service**  
**唯一主责：Crafting & Processing**  
**目的：**让后续 AI 一次处理一个可读、可验证的配方/加工步骤，避免把配方规则、库存、工作台、UI、存档和联网写成一个大系统。本卡不是新配方或游戏机制批准。

## 玩家体验目标

玩家能看懂“现在能做什么、缺什么、做出来有什么用”，并通过少量有意义的制作选择为下一趟出行、生活或家园成长做准备。新配方逐步引出新选择，不用庞大配方表和重复刷材料填充时长。

## 五款参考游戏如何转为原创规则

| 参考体验 | 在本模块中的设计约束 | 不照搬 |
|---|---|---|
| Crashlands | 收集到的材料应较快连到一个清楚的制作用途；完成反馈明确，玩家能看懂装备/物品为何有用。 | 不复制原作物品、怪物、制作树、数值或表现。 |
| Terraria | 新配方/站点可以随着区域探索和成长逐步开放；每次解锁扩展选择，而非平铺所有内容。 | 不复制 Boss、进度门槛、配方、矿物层级或 UI。 |
| Minecraft | 工作台与家园站点支持玩家安排自己的准备空间；可建造性由 HOME/Building 拥有。 | 不复制方块、合成格布局、配方或建筑风格。 |
| Don't Starve | 制作物服务可理解的准备与生存选择；成本、收益、失败原因先让玩家看懂。 | 不复制生存曲线、耐久惩罚、季节机制或物品效果。 |
| Stardew Valley | 制作节奏与家园生活、农场产出和社区成长相连，避免每分钟催促和机械化生产。 | 不复制具体机器、配方、村民关系、日历或素材。 |

这些只是体验取舍，不要求每个配方同时体现五款游戏。每个后续切片都要说明它对应的核心玩家收益。

## 唯一责任与跨模块交易边界

**Crafting & Processing 拥有：**稳定配方定义、配方解锁条件的消费、材料/站点/条件验证、加工规则、请求可行性，以及成功或可读失败结果。配方/内容 ID 与本地化文本由 **Content & Localization** 维护其目录合同。

- **Items & Inventory** 是物品数量与装备唯一写入者，负责原子扣料/加成。Crafting 只能提出结算请求，不能直接改数组、库存或存档键。
- **HOME & Building** 拥有站点 ID、位置、放置与升级；Crafting 只查询当前玩家是否满足站点条件。
- **Character & Progression / Quest & Narrative / POI & Exploration** 可提供已确认的解锁事实；Crafting 不直接授予经验、任务阶段、POI 发现或故事标记。
- **Time & Weather** 若未来配方需要时间/环境条件，只提供已确认快照；Crafting 不自建时钟。加工持续时间、离线加工和断线结算都需要单独合同。
- **UI & Map / Input & Accessibility** 显示配方状态并提交一次制作意图，不能直接扣材料或显示虚假成功。
- **Animation & Presentation / Audio & Feel** 只响应成功或失败结果；播放粒子、音效或弹窗不能构成制作成功。
- **Core State & Save / Network & Co-op** 负责持久化和共享。多人共享站点、并发制作、请求去重和存档迁移都需要单独验收；不由配方任务顺手改变协议或格式。
- 图标和站点外观由 **Asset Pipeline** 验证源素材，**Rendering & Camera** 验收采样/显示。美术不能定义配方、站点范围或碰撞。

**提议的事务语义（尚非现有 API）：**玩家提交制作意图 → Crafting 验证配方 ID、解锁、站点和输入条件 → Inventory 用唯一请求标识原子地扣除输入并加入产物 → 仅在 Inventory 确认成功后发出制作完成语义 → UI/动画/音频只表现确认结果。任一步失败都不得留下部分扣料或假成功。是否采用具体事件/API，须在选定实现任务时检查当前真实调用栈后再决定。

## 后续 AI 一次只能做一个小切片

选定一个已有且可核实的配方、配方分类或加工步骤，先检查 V21 实际启动顺序和 handler，回答：

1. 现在什么代码最终生效，材料 ID/物品图标从哪里读写，工作台位置/距离由谁拥有？
2. 配方解锁来自哪个已确认 owner？如果本地代码没有合同，先记录缺口，不自造第二份状态。
3. 请求重试、双击、并发与 Inventory 失败后怎样防止重复制作和部分扣料？
4. 新物品带来什么可见玩家价值，是否支持 HOME → 探索/准备的核心循环？

不得顺手建完整科技树、自动化工厂、多人共享库存、永久离线计时或新存档格式。没有明确 owner/事务合同则停在只读建议或设计草案。

## 高画质图标与制作表现门槛

制作菜单、物品图标、站点/加工动画遵循根目录 [`ART_BIBLE.md`](../../ART_BIBLE.md)：Modern High-Detail Pixel Art，边缘清楚、像素簇有设计、材质/形状能区分。高分辨率源图不能弥补导入后发糊、粗马赛克、压缩噪点或风格不一。

- 实施前从实际素材/渲染合同核对源尺寸、图集格、帧结构、锚点、alpha 和 nearest-neighbor 设置；没有证据的尺寸标 `UNKNOWN`，不擅自设图标尺寸或重采样。
- 源图与游戏实际画面并排检查，确认缩放和压缩后仍可辨别配方、数量、选中态和站点状态；图标层级不能混淆材料与产物。
- 在实际桌面 `1280×720` 和手机 `390×844` 游戏视口检查菜单排版、字号、图标边缘、长文本和触控命中区。缺少任一真实视口证据时标 `UNKNOWN / NOT ACCEPTED`。
- 单张概念图、静态网格、生成图或 Node 测试不能代表素材已接入、实际清晰或玩家体验通过。明显变糊、粗马赛克、裁切错误或难辨时标 `REVISE` 并指出源图、缩放/采样、图集合同或 UI 布局中的原因。

## 事务回归与相邻系统验收

- 材料恰好足够时，只完成一次；数量不足、错误站点、距离不符或未解锁时不扣材料、不产出。
- 双击、重复 request、并发制作以及客户端重试不能重复扣料或重复获得产物；Inventory 拒绝结算时不得发布完成反馈。
- UI、动画、音频只能在确认结果后反馈；关闭菜单、断线或失败不能伪造成功。
- 保持既有 Item ID、库存堆叠、save schema、Relay event 和站点位置合同；需要更改时拆出独立迁移任务。
- 改输入时回归 Input & Accessibility；改站点检查时回归 HOME & Building；改持久化/联网时必须跑 Save/Network 的专项合同及相邻回归。
- 测试通过只说明所覆盖路径通过。没有浏览器、实机视口或双客户端证据的项目明确标 UNKNOWN，不宣称全游戏无 Bug。

```text
唯一目标：【填写一个可核实的现有制作 Bug，或一个非常小的现有配方切片】。主责模块只能是 Crafting & Processing。先确认现有事实和唯一状态 owner，再列出精确允许文件、邻接接口、一次必要回归与一项相邻系统回归。默认只读审查/文档草案；明确授权实现时才改代码。

Inventory 独占物品数量写入，HOME 独占站点位置/身份。不得扩成完整科技树、工厂、好友交易、save schema 或 Relay 变更；不得覆盖、删除或擅自归因来源不明的文件。实现时先以测试证明所选行为，再做最小实现；串行跑相关测试并检查最终 diff。

```
